    Reverse engineering an ASIC from its GDS file

    August 11, 2026 · dhmb

    Jane Street put out a puzzle with the goal of reverse engineering an ASIC (Application-specific integrated circuit) from only a given GDS file (Graphic Design System). I have some experience with FPGAs so I thought let’s give this a try and learn a bit more about ASICs.

    As part of the puzzle there is a repository with a GDS file puzzle.gds, containing the layout of the ASIC. Also some input/output examples are given in a VCD file (Value change dump).

    There is a second GDS file warmup/04_final.gds meant as a warming-up for the actual puzzle. For this circuit we do have the original Verilog sources, netlist and DEF file (Design Exchange Format) so its functionality is known and can be used to verify the reversing logic.

    Inspecting the GDS files in KLayout#

    A GDS file contains information about how the ASIC is build up, layer by layer. Each layer is a 2D geometry, there is no information about the z-axis. What different layers mean and how they interact with each other is not captured in the GDS file, but is part of the PDK (Process design kit) being used.

    The full geometric structure is broken down into cells in a hierarchical way, cells can reference zero or more other cells, effectively creating a tree of cells (more precisely, cell instances). It is important to understand the different between a cell definition and a cell instance. The file contains exactly one cell definition for each cell type, but can have many instances of that particular cell type. Each cell reference has an origin, an angle by which it is rotated and a flag whether it is flipped in the x direction. This fully defines its location on the grid. An optional repetition can be defined, but in this puzzle we will not encounter this.

    Each individual cell has a name and contains objects such as polygons, paths and labels. Each of these objects is tight to a certain layer and datatype and if defined by its geometry, polygons and paths are defined by polygons and labels are defined by a point.

    The GDS file can be opened and visualized in KLayout. On the left side the hierarchy of cells is shows (note that each cell definition is only shown once, even though it can be referenced multiple times by the same parent cell, leading to multiple instances of that type). The right side shows all the layers in the layer/datatype format. In the middle the actual geometry is shown. In case of the warm-up file 04_final.gds this looks like:

    The touching layers are connected to each other (at least logically). For layer li1 upwards that means they are electrically conducting, creating many different conducting nets. Those nets are connected to the standard cells that we saw earlier. Different nets connect to different pins on those cells. This create a large (directed) graph with the pins of the cells as nodes and the nets being the edges. At this point we only focus on li1 upwards, assuming whatever happens under there is an implementation detail of the standard cell which we can ignore (at least for now). We also focus only on the logical pins and ignore pins like VGND, VPWR, VPB and VNB. Finally there are some physical-only (non-functional) cells that are not relevant for the implemented logic (sky130_fd_sc_hd__decap_3, sky130_fd_sc_hd__tapvpwrvgnd_1 and sky130_fd_sc_hd__diode_2) and we ignore them too.     The layers with suffix _LBL contain the labels, which can be used to identify the pins of the different cells. They are points, not polygons.

    For the warmup circuit this works very well, all input pins are connected to output pins of cells. For the top-level input and output pins we introduced ‘virtual’ cells just so all pins can be handled uniformly. In case of the actual puzzle some input and output pins are not connected. Specifically we have:

    • 15 output pins X of sky130_fd_sc_hd__clkbuf_4 cells are not connected
    • 5 output pins HI of sky130_fd_sc_hd__conb_1 cells are not connected
    • 1 output pin LO of a sky130_fd_sc_hd__conb_1 cell is not connected
    • 1 input pin A1 of a sky130_fd_sc_hd__a31oi_2 cell is not connected
    • 1 input pin A1 of a sky130_fd_sc_hd__a311o_2 cell is not connected

Also the disconnected clock buffers might just be symptom of what Claude referred to as clock-tree-synthesis over-provisioning. For now these dangling outputs will just be ignored.

    Implementation in Python#

    from shapely import STRtree

def _get_connected_components(adj: Sequence[Sequence[int]]) -> Sequence[Sequence[int]]:
    visited = [False] * len(adj)
    components: list[list[int]] = []

    for start in range(len(adj)):
        if visited[start]:
            continue

        component = []
        stack = [start]
        visited[start] = True

        while stack:
            node = stack.pop()
            component.append(node)

            for neighbor in adj[node]:
                if not visited[neighbor]:
                    visited[neighbor] = True
                    stack.append(neighbor)

        components.append(component)

    return components


class NetList:
    library: GdsLibrary
    components: Sequence[Sequence[int]]
    component_map: Sequence[int]
    cell_map: Mapping[int, Sequence[int]]

    def __init__(self, library: GdsLibrary, conduction_list: Iterable[tuple[Layer, ...]]):
        self.library = library

        # Use adjacency list, index in the list is the id of the element,
        # implying that this can only be used on top library (which has consecutive ids).
        # An indirection is needed to make this work for child libraries.
        adj: list[list[int]] = [[] for _ in library.elements]
        cell_map: dict[int, list[int]] = {}

        # Note that we are repeating checks within each layer itself,
        # that's ok for now we will de-duplicate
        for conduction_tuple in conduction_list:
            elements = library.by_layers(conduction_tuple).elements

            geometries = [e.geometry for e in elements]
            tree = STRtree(geometries)
            for i in range(len(elements)):
                candidates = tree.query(geometries[i])
                for j in candidates:
                    j = int(j)
                    if j > i and geometries[i].intersects(geometries[j]):
                        i_id = elements[i].id
                        j_id = elements[j].id

                        adj[i_id].append(j_id)
                        adj[j_id].append(i_id)

        # De-duplicate
        adj_tuple = [tuple(set(l)) for l in adj]

        self.components = _get_connected_components(adj_tuple)

        component_map = [-1] * len(library.elements)

        for i, component in enumerate(self.components):
            for element in component:
                assert component_map[element] == -1
                component_map[element] = i
                cell_id = library.elements[element].cell_id

                components_in_cell = cell_map.setdefault(cell_id, [])
                if i not in components_in_cell:
                    components_in_cell.append(i)

        self.component_map = tuple(component_map)
        self.cell_map = cell_map

    As long as the list of candidates is relatively short this will be much faster than pair-wise checking all polygons. Note that _get_connected_components will merge connected parts over the different tuples of the conduction list.

    Removing non-logic cells#

    The nodes in the netlist graph can be split in five categories:

    Node typeDescription
    Input nodesContaining the input pins, including potential dummy pins
    Output nodesContaining the output pins
    Boolean cellsStandard SKY130 cells implementing different boolean logic
    State cellsCells that hold values as state, several standard SKY130 flip-flop cells
    OtherNon-logical cells, specifically standard SKY130 (clock) buffer cells

    The (clock) buffer cells do not perform any logic, their purpose is to make sure signals arrive correctly and on time (e.g. low clock skew) for large and deep circuits. From our point-of-view they are not interesting so we just remove them. This is trivial, they have a single input and output pin so we can just remove them and reconnect the pins. There are four cell types in this category, sky130_fd_sc_hd__buf_2, sky130_fd_sc_hd__clkbuf_4, sky130_fd_sc_hd__clkbuf_8 and sky130_fd_sc_hd__clkbuf_16.

Also it does not propagate through other cells, it’s just a simple way to clean the edges from the input pins.

    Merge muxed resettable flip-flops#

    This step is more interesting, two different cell types will be merged into a new cell. A common structure that can be found in the netlist is:

    The sky130_fd_sc_hd__mux2_1 cell is a multiplexer, depending on the input signal S it selects either A0 (S=0) or A1 (S=1) as output X. On its own it can be considered a boolean gate, implementing logic X = (~S & A0) | (S & A1).

    The sky130_fd_sc_hd__dfrtp_2 cell is a type of flip-flop, specifically a data flip-flop with an active-low asynchronous reset. A data flip-flop means that it captures the value D at some specific moment in the clock cycle (positive-edge triggered in this case). An active-low reset means that it resets to its default value 0 as soon as RESET_B=0 (this is also indicated by the _B suffix of the pin, which means active-low here). Asynchronous reset means it resets asynchronously from the clock, as soon as RESET_B=0.

    When put together in this exact formation (the X output pin of the multiplexer connects to the D data pin of the flip-flop, and the flip-flop Q output pin feeds back into the A0 input pin of the multiplexer), the two cells acts together as a data flip-flop with enable bit. As soon as the enable bit is high, a new bit value from A1 is loaded on each clock cycle. When the enable bit is low, the flip-flop is retaining its original value, ignoring A1.

    Two things to note here:

    1. This particular part of the graph shows that we are not dealing with a directed acyclic graph (DAG), there can be cycles/feedback. This is not a problem, since the signals do not propagate instantaneously, the internals of the flip-flop guarantee all pin values are well-defined.
    2. You can see three input pin values being propagated here, as a result of the previous step. The S pin of the multiplexer is directly connected to the en enable pin, RESET_B and CLK on the flip-flop are directly connected to the rst_n reset pin and clk clock pin.

    These two cells can be merged into a single new cell, I called it the MuxedResettableFlipflop:

    The A0, X and D pins are absorbed, the A1 pin still functions as input (in case of S=1). The output pin Q still exists, it just has one less edge (the one that used to go A0 is gone).

    The warmup circuit has 16 of these flip-flop/multiplexer combinations.

    Merge into shift registers#

    When positioning the newly merged MuxedResettableFlipflop together it becomes clear there are two pairs of 8 flip-flops, within each pair they are connected in serial:

    It is a bit hard to see because of all the edges going off to the right, that is where all the boolean logic cells are.

    Having these flip-flops in serial means that as long as the enable bit is active, on each clock cycle, the first flip-flop reads the new incoming bit, the second one reads the first bit, the third one reads the second bit and so forth, so the bit values shift through the different flip-flops. This is exactly how a shift-register operates. So a second pass over the graph is implemented to merge MuxedResettableFlipflop’s that are connected in serial into a single new cell, the ShiftRegister:

    The size of this cell is parameterized, depending on the length of the chain of flip-flops it originates from. For each flip-flop there is an output pin, and there is a single (data) input pin, A from where the bits shift in.

    When implementing this reduction it’s important to do it correctly and reduce the full chain. A greedy algorithm, that would merge a chain as soon as it visits a flip-flop, might end up reducing only the tail of a longer chain. An easy (probably sub-optimal) way would be to visit all cells, get a list of potential ShiftRegister-merges, then select the largest one and reduce it. Repeat this until no more reductions are possible.

    Reducing logic network#

    For the warmup circuit we now end up with the input cell with a couple of pins, two 8-bit shift registers, then a hole network of logic gates (containing 44 cells) and finally the output cell with a single success pin. I see two approaches for reducing the logic network:

    1. Somehow undo all the optimization and retrieve the original functionality (which, from the warmup/00_source.v file in the puzzle’s repository, we know much be logic to do the addition and a comparator with the constant 496)
    2. Consider the logic network to be a black box and somehow solve for the output pin to be success=1.

    The first option seems complicated and probably will not map well on more completed circuits. Using the second approach, the whole network of boolean gates can be merged into a single BooleanFunction. It has 16 input pins and a single output pin, and encapsulates all logic performed on the two 8-bit inputs. Mathematically this could be represented as x = F(q), with q a 16 bit input and x the single bit output. The boolean function F represents all the logic. After implementing the second option the circuit now looks like:

    Adding support for solving this is straightforward, it’s a DAG of boolean logic gates without any state, so any SAT solver can do this. I originally wanted to use Z3 since I have some experience with it and there is a Rust package. Unfortunately these are just bindings to the C libs so they won’t work when targeting WASM. Instead I went with BatSat, which can be used with WASM targets as well. The bits of the shift registers can be interpreted either directly as bits, or as a decimal number. This results in a simple interface:

    Applying to the puzzle#

    Applying these steps to the actual puzzle is straightforward except for the last step. In the warmup the situation simple, all state cells came before the logical cells, so there was a single, well-defined boolean function that described all the logical cells. For the puzzle it is much more complex. There is only one shift register (12 bits wide), and there are many separate flip-flops, representing regular registers. Many logical cells are not on a clear path towards a single register, but shared by many. To make this more precise, for each register and output pin we can define its cone of influence. It’s the set of input pins, logical gates and registers that directly influence its value. It’s important to realize that this is not a partition of the graph, many cells are part of the cone of influence of multiple registers and pins.

    To solve this my approach was to merge the logic gates in boolean functions, but where needed split them in multiple functions, that could be parts of the cone of influence of multiple registers/pins. This reduced the graph significantly, but still made it incomprehensive for me.

    To give a feeling for how effective these steps are I made table with the graph size after each step (the steps are cumulative):

    StepsWarmup cellsWarmup edgesPuzzle cellsPuzzle edges
    Original graph812077302042
    Removing non-logic cells782046972009
    Propagate pin values781566971784
    Merge muxed resettable flip-flops621246851760
    Merge into shift registers481106741738
    Reducing logic network519229738

    As we saw the warmup graph gets reduced to only 5 cells, the puzzle still contains 229 cells, around a third of the original size. I thought a bit about how to improve this, but didn’t see any quick wins. At this point I lost interest in further reduction, and just wanted to solve the puzzle.

    Solving the puzzle#

    With the netlist of the puzzle still quite complex I started thinking how to solve it. The input pin propagation made clear there is only one clock domain, all state cells are connected directly to the same clock signal (potentially via a buffer, but that is irrelevant here). So there is no clock domain crossing. Also the reset button is shared by the state cells and the enable button is connected to a single logic cell, although this is not crucial for solving the system.

    Mapping on a finite-state machine model#

    The fact that there is a single clock domain means we can treat the whole circuit as a finite-state machine (FSM), by assuming that every clock cycle the system transitions from state i to state i+1. This means that when we map the netlist on a FSM, the clock pins are no longer present.

    When changing to this FSM model, some details are lost. For example the asynchronous reset that was discussed earlier no longer exists. There is no asynchronicity in a finite-state machine, except for the discrete state transitions. For solving the puzzle these type of details are not relevant though.

    Mathematically the system can be modelled as:

    $$ (s_{t+1}, y_t) = F(s_t, x_t) $$

    Here $s_t$ is the state, so the values of all flip-flops/registers. $x_t$ are the input values, in this case the values of the input pins I, enable, rst_n and the dummy pin dummy1, corresponding to the dangling net in the netlist that was discussed earlier. $y_t$ is the output state, so the values of the output pins success and the 8 pins O[0]...O[7]. So $s_t$, $x_t$ and $y_t$ should be seen as bit-vectors. The function $F$ contains all the logic to transition from one state to the next, basically encapsulating all logic from the circuit. If you would write it out it would look quite complex, but it’s really just all the gates and flip-flops put together, so it’s individual parts are simple.

    Initial state#

    Special care is needed for the initial state. The input pins are free variables in this model, so $x_0$ will be determined during the solving. The initial values of the flip-flops (and thus the registers) are the initial state $s_0$, and they need to be well-defined. To solve this we assume an implicit reset has taken place before state 0. In the case of the puzzle this means the rst_n pin was implicitly assumed to be 0 (_n means bit-inverting here, similar to _B), resetting all flip-flops are resettable. Flip-flops with a SET_B pin are initialized to 1, and flip-flops with a RESET_B pin to 0.

    There are four flip-flops that cannot be reset, the cells of type sky130_fd_sc_hd__dfxtp_2. They are the most basic data flip-flops, taking on the value of their input pin D unconditionally. This means that during the initial state they do not have a well-defined value yet. The solver treats them as free variables (equivalent to the input pins). At any later cycle they are just handled as regular state variables. We will see that this approach works fine, their exact initial value most likely has no influence on the final solution because their input logic sets them to specific values at some point.

    Unrolling the states#

    With the current model we can start solving, but only for the first time-step. We can put constraints on the output vector $y_0$ and see if there is a solution that satisfies those constraints. In particular we are interested in success=1. Of course this will be unsatisfiable, it would not really be a puzzle if we can find the solution in a single clock cycle. So there are two problems:

    1. How do we solve over multiple cycles?
    2. How do we know how many cycles are actually needed?

    For the first problem we need to un-enroll the states. Assume we want to allow for 2 clock cycles to run. We then have the coupled system:

    $$ (s_1, y_0) = F(s_0, x_0) \\ (s_2, y_1) = F(s_1, x_1) $$

    Now the trick is to create one big system that captures both cycles. After a bit of thinking this is not that hard. The input, state and output of the full system just become the union of the input, state and output of each cycle. If we call the new function $F_2$ this can be written as:

    $$ (s_{1,2}, y_{0,1}) = F_2(s_{0,1}, x_{0,1}) $$

    $F_2$ is of course much more complicated than $F$. It depends on twice as many variables, and future states and outputs depend on previous states and inputs. The process of creating it is mechanical though, and can be trivially extended to more cycles, so this solves the first problem.

    Finding the required number of cycles#

    We can now solve for a specific number of cycles and see if there is a sequence of inputs that satisfies success=1. We still don’t know how many cycles are needed, specifically what the minimum number of cycles is. A simple and efficient sequence to find the minimum number of cycles is:

    1. Use exponential search for finding an upper bound, that is keep increasing the number of cycles with some factor (say 2) until we find a solution.
    2. Given that upper and lower bound (the second last try would have failed, so it’s a lower bound) we can use binary search to find the minimum number of cycles needed.

    This means we first increase the number of cycles, e.g. 0, 1, 2, 4, 8, 16, 32, etc, until an input sequence is found that gives success=1. So if 32 succeeds we can further narrow it down by doing a binary search between 16 and 32, e.g. 24, 28, 30, 29 (assuming 29 is the correct number). This gives the answer in 11 evaluations instead of 29. The higher the required number of cycles the better the gain compared to just trying all numbers one by one.

    Finally: solving the puzzle#

    Finally the puzzle can be solved. After adding the solver to the tool, and setting the success=1 constraint it finds a solution. The solver required 15 iterations, with the number of cycles respectively 0, 1, 2, 4, 8, 16, 32, 64, 128, 96, 112, 120, 124, 122 and 121, with 122 cycles the minimum number of cycles to find a solution satisfying the constraint.

    Focussing on the successful 122 cycle solve, the corresponding input sequence is:

    Enumerate output messages#

    At this point we can consider the puzzle solved. Of course the question is: are there more output messages, and how can we enumerate them.

    Given that we are using a SAT solver to solve the system, it is easy to add additional constraints. Specifically we can add constraints to the output bus O for specific cycles.

    To retrieve the original message (* TWO STARS *), we adapt the solver to a fixed number of cycles, say 140. This way we force it to solve beyond the output message. Additionally we add a constraint on O:

    O@122 == '('

    This means that at cycle 122 the output bus should show ( (we know this is satisfiable, it’s exactly the solution we found earlier). In the tool the constraint can be encoded using an ASCII character, under the hood it’s translated to the required binary constraints on the specific output bits within the unrolled output bit vector.

    Now we can add a more interesting constraint. We require some message to start at cycle 122, but with a different starting character:

    O@122 != 0x00
O@122 != '('

    This turns out to be unsatisfiable. Of course this means only that whatever success message we get, it will start with (. Repeating this for each individual character (all the way to O@136 != ')') shows there is no other success message.

    There still could be messages for the success=0 case. I was thinking about writing some logic to automatically enumerate them, but decided to just play manually with the constraints, I did not expect there to be too many possibilities.

    The case of the floating inputs#

    Now there are still two points unaddressed:

    1. At the start we found that two logic gates were connected to the same floating net, this is why we introduced the dummy1 input pin,
    2. The very last message we found seems mangled: TWO NOT TOUCJ.

    Interestingly these two observations are connected. If we apply a merge by cone of influence, and do this for each individual output bit (by setting one by one O[0], O[1] all the way to O[7] as single output pin for which the cone is determined), only two values have the dummy1 input pin in their cone of influence, O[1] and O[4] (note that success also does not have the dummy1 pin in its cone of influence). So this means that only those two bits are influenced by the dummy1 value.

    If we expand the unexpected J from TWO NOT TOUCJ and the two suffix bytes 0x02 and 0x10 in binary we have:

    J     01001010b
0x02  00000010b
0x10  00010000b

H     01001000b

    This all makes sense, all characters J, 0x02 and 0x10 have either bit 1, bit 4 or both mangled (remember, counting from least-significant first, so right-to-left, 0-based).

    This is confirmed by flipping the dummy1 bit. The solver choose it to be 1. If we change it to 0 the output becomes TWO"NOT TOUCH, so a " instead of a space for the fourth character.

    "     00100010b

0x20  00100000b

    Again bit 1 is mangled, so fully consistent with the floating gates. This makes me quite confident the disconnected logic gates are just a bug somewhere in the pipeline of making the GDS file, this does not seem like an intentional easter egg.

    Conclusion#

    There are no more easter eggs to be found I think. It could be that there is still something hidden going on inside the circuitry itself, but I decided to move on. I think the big take-away here is that if you purely want to solve the puzzle with circuits this size you can move directly to a SAT solver. For me the process of reducing the circuit was interesting (specially the warmup circuit), and showed how higher level components such as a shift register map on the actual flip-flops and other low-level cells. It was also a fun exercise to see how far vibe-coding a tool would bring me, which worked surprisingly well. If you are more interested in how the SAT solver is set up, and how the mapping works in detail this might be disappointed for you, but for me using Claude was great, it made sure I could finish the puzzle without having to spend a lot of time on boiler plate code (or at least relatively simple business logic etc). This way I did not lose my motivation before finishing.

    The tool that I used for the analysis can be found at https://dhmb.github.io/netlist-simulate (source code is at https://github.com/dhmb/netlist-simulate).
